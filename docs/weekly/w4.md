## 1. 本周做了什么

按设计 11 节顺序完成 7 步，W3 的 `VerificationIssue` / `VerificationResult` /
`PARTIAL_ANSWER` 契约未改。

1. **依赖与契约**：FastMCP 4.1.3 在 Python 3.13 上完成 import/stdio smoke；
   `mcp/schemas.py` 统一成功/错误信封、错误码、`SearchArticlesRequest`、
   `UserProfile` 与响应模型。工具参数中的枚举/日期用字符串接收并在服务端
   手工校验，非法值返回 `INVALID_FILTER` / `INVALID_ARGUMENT`，不透传
   Pydantic traceback。
2. **混合索引**：payload 增加学院、专业、入学年份、阶段、培养类型、群体、
   学籍状态、学年字段与 payload index；BM25 sparse 与 dense 同时写入
   `articles_v1`；manifest 记录 sparse vocab/idf 版本、点数、source hash 与
   `index_version`。重建使用 `--recreate`，避免旧 dense-only 点混入。
3. **混合召回**：dense/sparse 各取 top 30，RRF(k=60) 融合，按
   `(article_id, part_no)` 去重、按 `article_id` 聚合最高 RRF 片段；同一文档
   只按“版本”裁剪旧版，保留最新版本下的全部条款。bge-reranker-v2-m3
   重排后应用阈值、margin 与 token budget。
4. **MCP servers**：`policy-search` 提供 `search_articles` / `get_article`；
   `policy-meta` 提供 `get_document_versions` / `get_document` /
   `resolve_version` / `list_documents`。未注册 flow/calendar 伪工具；
   客户端检查 tool list，缺失时返回 `NOT_IMPLEMENTED` 并说明 W5 提供。
5. **client 与 QAService**：stdio 后台事件循环 + 持久会话；单次调用 30s
   超时、可重试错误重试 1 次；连接失败映射 `TOOL_UNAVAILABLE`，索引错误映射
   `INDEX_UNAVAILABLE`。QAService 改依赖 `SearchClient` 协议，接受
   `profile`，校验 `index_version`，trace 增加 `mcp` / `retrieval_timing` /
   `index_version` / `retrieval_warnings`；`version_metadata` 通过 policy-meta 读取，只进 trace。
6. **受众/时间过滤**：`UserProfile` 与文档细目按“空 = 不限制”过滤；
   未知用户字段保留并返回 `PROFILE_UNDETERMINED`，未指定受众返回
   `AUDIENCE_UNDETERMINED`；支持 current / historical / include_repealed、
   `as_of`、学年 cycle 与同生效日版本冲突。
7. **评测/文档**：dense-only vs hybrid RRF vs hybrid+rerank 的 20 题检索对比；
   5 个人群错配 case 通过 MCP 实跑；W3 回归使用独立 run，不覆盖 W3 基线。

## 2. sparse 选择与索引

W4 默认 **BM25 风格 sparse**，不引入额外模型：

- 中文单字 + 相邻双字，英文/数字按连续串小写；
- `k1=1.2`、`b=0.75`，IDF 使用 `log(1 + (N - df + 0.5)/(df + 0.5))`；
- token 经 blake2b 稳定映射到 uint32；同一 vocab/idf 写入
  `data/sparse_vocab.json`，查询端只读加载；
- 文档向量存饱和 TF，查询向量存 IDF，Qdrant 稀疏点积即 BM25 分数；
- `SparseEncoder` 协议保留 bge-m3 sparse 替换点，MCP schema 不变。

实测：3,952 块，`avg_doc_len=413.7`，vocab 文件 2.5 MB；
`embedding_mode=hybrid`，device=cuda。

## 4. 检索评测（dev_v0 20 题）

`data/eval/w4-retrieval-report.{json,md}`；不调用 LLM；非可答题不计入检索指标。

| 模式 | article Recall@8 | article MRR | section Recall@8 | section MRR | overall Recall@8 | overall MRR |
|---|---:|---:|---:|---:|---:|---:|
| dense-only（W3 基线） | 1.000 | 1.000 | 1.000 | 0.333 | 1.000 | 0.905 |
| dense+sparse RRF | 1.000 | 0.822 | 1.000 | 1.000 | 1.000 | 0.848 |
| RRF + bge-reranker-v2-m3 | 1.000 | 0.958 | 1.000 | 0.750 | 1.000 | 0.929 |

延迟（检索层，warm）：

| 模式 | p50 | p95 | rerank p50 / p95 |
|---|---:|---:|---:|
| dense-only | 131.5 ms | 359.0 ms | n/a |
| hybrid RRF | 214.0 ms | 637.2 ms | n/a |
| hybrid + rerank | 1,325.5 ms | 1,677.4 ms | 1,038.0 / 1,474.5 ms |

解读：

- Recall@8 三种模式都是 1.000；混合召回没有丢目标条款；
- 单看 RRF，article MRR 低于 dense（0.822 vs 1.000），说明 BM25 词面匹配
  会把短条款排到前面；不能宣称“混合召回一定更好”；
- 加 reranker 后 article MRR 0.958、overall MRR 0.929，优于 dense 0.905；
- reranker 把 p95 从约 0.36–0.64s 拉到约 1.7s，是 W4 的主要延迟成本；
- 阈值用 dev_v0 校准：可答题 top rerank 最低 0.725，非可答题最高 0.523，
  取 `min_rerank_score=0.60` + `margin=0.03`；这是开发集证据，不是冻结结论。

**实现过程中修复的一个缺陷**：最初的版本聚合按 `doc_id` 只保留最高 RRF 的
一条条款，导致 d001/d009 等同文档多条款问题丢条款；修复为“按版本裁剪旧版，
保留最新版本全部条款”后，dense/RRF/rerank 的 Recall@8 才恢复到 1.000。
该回归由 `test_multiple_articles_of_same_document_are_both_kept` 固定。

## 8. 限制

- dev_v0 只有 20 题，不是冻结测试集；W4 不宣称答案质量提升。
- RRF 单独使用会降低 article MRR；reranker 才是排序收益来源，代价是约 1s
  检索延迟。
- `min_rerank_score=0.60` 只在 dev_v0 上校准，可能对未覆盖问题过严/过松。
- BM25 对“种子科学 → 农学”这类语义改写不敏感；case 4/5 的召回缺口需要
  W6/W7 处理。
- 历史版本问答仍由 W3 guard 拒绝；`policy-meta.resolve_version` 已提供工具，
  但完整历史回答留 W6。
- flow/calendar 工具未实现；客户端明确返回 `NOT_IMPLEMENTED`，不返回空数据。
- MCP server 冷启动（bge-m3 + reranker）约 30–60s，已从每轮 p95 中排除；
  server 崩溃/超时会让 QAService 明确拒答，不会无引用作答。
